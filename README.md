## 1 Introduction

### 1.1 What karma is

karma is task and knowledge organization for agent-first workspaces. It gives everyone, human and agent, one durable record of the work, its state, and what was learned along the way. A `karma` CLI drives the record. Plain markdown files hold the content. A SQLite database holds the state.

### 1.2 The problem it solves

By default, agents working in a workspace share nothing. Each agent keeps its own notes. Each plan lives in its own file. When the session ends, the context ends with it. Nobody, human or agent, sees the whole picture. karma fixes that with one record that every agent and every human reads and writes through the same commands. The scatter becomes a single source of truth, and it stays.

### 1.3 Built for agent coordination

Every work-tracking tool on the market assumes a human clicking. karma starts from a different assumption: an agent driving the loop, and a human reading the trail. That one shift changes the design center:

- **Tasks and agendas are a coordination log.** An agent, or you, records what work exists and what state it is in. A swarm reads the same log, claims work, and records transitions. The per-agent `plan.md` file stops being the only source of truth.
- **Memory is the contextual share.** Decisions, gotchas, and handover notes live in queryable, git-backed spaces. One agent deposits a lesson. Every future agent gets it instead of re-deriving it.
- **Together they let swarms coordinate.** Several agents can work one workspace in parallel. The record of who is doing what, and the context behind it, is shared, not scattered.

And this is not an agent-only tool. You can drive the same nouns yourself, for personal work, team work, or both at once. See [Solo mode](#91-solo-mode).

### 1.4 The four layers

karma gives each layer exactly one job:

| layer | job | truth of |
|---|---|---|
| `.karma/karma.db` | the index | state (what exists, scopes, statuses, counters) |
| the `karma` CLI | the control panel | the only path to state mutation |
| markdown files | the content | task bodies, memory items |
| you and your agents | the drivers | everything else |

The database never holds content. The disk never holds state. Each restriction earns its keep. Because state lives in one file, state recovery is restoring one file. Because content lives in plain files, every editor, `grep`, and `ls` already works. And because the CLI is the only mutation path, the oplog, the database's append-only state history, records every mutation in the same transaction. Log and state can never disagree.

### 1.5 What karma is not

- **No graphical interface.** The CLI and the files are the interface.
- **Not an enterprise tracker.** karma complements Jira, Linear, and friends. It tracks the slice of work agents actually drive, not the whole org backlog.
- **Not the agent documentation.** Every workspace ships its own agent-facing docs after `karma init`. This manual teaches you, the human. See [What your agents receive](#33-what-your-agents-receive).

### 1.6 Who this manual is for

If you supervise a workspace where agents work, this manual was written for you. If you use karma solo, it works for you too. Either way, the path is the same: concepts first, then a hands-on tour, then each feature in depth, then operations, recipes, and troubleshooting. Read it front to back once, then keep it within reach.

## 2 Core concepts

Everything in karma rests on a small set of ideas. This chapter builds them one at a time. Five minutes here makes every later command feel obvious.

### 2.1 The workspace

`karma init` creates one directory, `.karma/`, in the current directory. That directory is the workspace:

    .karma/
      karma.db       # the index, never edit directly
      karma.db-wal   # write-ahead log (transient)
      karma.db-shm   # shared memory (transient)
      readme.md      # the primer, regenerated by init
      docs/
        manual.md    # every command: what it does, accepts, returns, changes
        usage.md     # processes: the daily loop, memory discipline, drift fixes
      work/          # task and agenda bodies (WK<n>.md)
      memory/        # one git repo per memory space (ME<n>/)

Every `karma` command walks up from the current directory to the nearest ancestor `.karma/`. Run commands from anywhere inside your project.

### 2.2 The five nouns

Everything in karma is one of five nouns:

| noun | id | lives on disk | nature |
|---|---|---|---|
| project | slug | nowhere (database only) | optional scope with its own status and priority enums |
| task | `WK<n>` | `work/WK<n>.md` | atomic job (the file is the body) |
| agenda | `WK<n>` | `work/WK<n>.md` | parent of tasks, sharing the WK counter |
| memory | `ME<n>` | `memory/ME<n>/` (git repo) | running knowledge space |
| memory item | `ME<n>#<seq>` | `memory/ME<n>/<seq>-<slug>.md` | one authored md file |

### 2.3 Tasks and agendas

A **task** is one job. An **agenda** groups tasks. Both are work items, both share one `WK` counter, and both live as one markdown file in `work/`. Two rules hold the hierarchy simple:

- A parent must be an agenda. A child must be a task.
- Agendas do not nest.

The CLI enforces both rules at every mutation, so it never has to police a hierarchy the schema cannot express.

### 2.4 Projects as scopes

A project is an optional scope with its own vocabulary: a status enum and a priority enum. Tasks and agendas created inside a project get the project's rank-1 status and priority. Items created outside any project are **standalone**: they have no status and no priority, and they render as backlog.

    karma project create ops --title "Operations" \
        --statuses "TODO,DOING,BLOCKED,SHIPPED" --priorities "P1,P2,P3"

Standalone items can join a project later. See [Props](#46-props).

### 2.5 Memory

Memory is the workspace's running knowledge: decisions and their reasons, gotchas, handover notes, anything a future session should not have to re-derive. It has two levels. A **memory space** (`ME<n>`) holds one theme. A **memory item** (`ME<n>#<seq>`) is one lesson inside it.

Each space is its own git repository at `memory/ME<n>/`, not one big repo for the whole workspace. Per-space repos keep every theme's history self-contained: a space can be read, backed up, or discarded wholesale without touching another theme. Items are plain markdown files, authored only through the CLI. The file is the content truth. Every mutation re-authors the file and records one git commit, so `git log` is the timeline of what you knew and when. [Chapter 5](#5-memory) covers the day-to-day.

### 2.6 IDs and the no-delete rule

IDs are monotonic and never reused or renumbered:

| noun | id | counter |
|---|---|---|
| project | slug (unique) | — |
| task, agenda | `WK<n>` | workspace-global, shared |
| memory | `ME<n>` | workspace-global |
| memory item | `ME<n>#<seq>` | per-space |

Deletion does not exist for work items: they **archive** (a restorable freeze). Memory spaces and items **discard** (destructive and gated). A discarded item's sequence dangles forever. It never rebinds. Concurrent agents interleave IDs, so never assume `id+1`. Parse the ID each create prints.

### 2.7 Drift is reported, not prevented

karma does not block you from breaking the contract. It detects the break. `karma health` compares the database against the disk and names every finding: hand-edited memory files, dangling links, missing files, orphans, counter drift. Enforcement beyond detection is a non-goal. The primer states the contract. Health catches the violations. See [Health and recovery](#7-health-and-recovery).

## 3 Getting started

Everything in this chapter starts from zero: install the binary, initialize a workspace, and run one follow-along session.

### 3.1 Install

On macOS, install through Homebrew:

    brew install coenesis/tap/karma


This manual assumes the `karma` binary is on your PATH. One command then takes an empty directory to a living workspace.

### 3.2 karma init

Run `karma init` in your project's root directory:

    $ karma init
    initialized: /Users/alice/projects/website/.karma (schema v6)

`init` is idempotent. Running it again regenerates `readme.md` and `docs/` and changes nothing else:

    $ karma init
    already initialized: /Users/alice/projects/website/.karma (schema v6)

To also install the agent skill, see [Agent setup](#62-agent-setup):

    $ karma init --with-skill
    already initialized: /Users/alice/projects/website/.karma (schema v6)
    skills: /Users/alice/projects/website/.agents/skills (upgrade refreshes this copy)

The bare flag installs to `.agents/skills/` beside `.karma/`. A value installs to that directory instead: `karma init --with-skill /path/to/skills` puts the skill there, and relative paths resolve against the current directory. Either form records the location in `.karma/skills-root`, so `karma upgrade` refreshes the right copy.

One surprise to avoid: running `init` inside a subdirectory of an existing workspace creates a separate nested workspace, and the nearest `.karma/` wins for every command.

### 3.3 What your agents receive

After `init`, every agent working in the workspace can read four things:

- `.karma/readme.md`: the primer, the contract, the nouns, the rules.
- `.karma/docs/manual.md`: every command, what it does, accepts, returns, and changes.
- `.karma/docs/usage.md`: processes, the daily loop, memory discipline, and how to fix drift.
- the `karma-usage` skill, installed by `init --with-skill`, where agent harnesses discover it.

Your agents read these on every session. You rarely need to. This manual covers the human side.

### 3.4 A follow-along first session

Type these commands in your project. Every output below is real.

**1. Create a project with your own vocabulary:**

    $ karma project create ops --title "Operations" \
          --statuses "TODO,DOING,BLOCKED,SHIPPED" --priorities "P1,P2,P3"
    project ops created — statuses: TODO, DOING, BLOCKED, SHIPPED — priorities: P1, P2, P3

The flags are optional. `karma project create ops` alone creates the project with default statuses (OPEN, ACTIVE, PAUSED, DONE, DROPPED). This tour sets its own vocabulary so the statuses read like a real board.

**2. Create an agenda, the umbrella for a piece of work:**

    $ karma agenda create "Website relaunch" --project ops
    WK1
      title    Website relaunch
      status   TODO
      priority P1
      file     work/WK1.md

**3. Create a task under it:**

    $ karma task create "Draft landing page copy" --project ops --agenda WK1
    WK2
      title    Draft landing page copy
      status   TODO
      priority P1
      agenda   WK1
      file     work/WK2.md

The task got `TODO` and `P1`, the rank-1 values of the project's enums. The printed ID (`WK2`) is the task's address for every future command. Both flags matter, by the way: karma does not inherit the agenda's project. The agenda already lives in one, and a child must share it or the create fails. [Agendas](#43-agendas) covers the rule and the reconcile flow for when scopes disagree.

**4. Create two more, one in the project and one standalone:**

    $ karma task create "Buy SSL certificate" --project ops
    WK3
      title    Buy SSL certificate
      status   TODO
      priority P1
      agenda   —
      file     work/WK3.md

    $ karma task create "Personal: renew passport"
    WK4
      title    Personal: renew passport
      status   — (standalone)
      priority —
      agenda   —
      file     work/WK4.md

**5. See the board:**

    $ karma task list
    id   status  priority  project  agenda  arch  updated                    title
    ---  ------  --------  -------  ------  ----  -------------------------  ------------------------
    WK2  TODO    P1        ops      WK1           2026-10-21T01:56:56+05:30  Draft landing page copy
    WK3  TODO    P1        ops      —             2026-10-21T01:57:00+05:30  Buy SSL certificate
    WK4  —       —         —        —             2026-10-21T01:57:03+05:30  Personal: renew passport

`task list` shows tasks. Agendas have their own list (see [Agendas](#43-agendas)). `WK4` came with no `--project`, so it is standalone: no status, no priority.

**6. Write the body.** Task bodies are plain markdown files. Open `.karma/work/WK2.md` in any editor and write the plan:

    # Landing page copy - plan

    1. Hero: one sentence on what the product unblocks.

**7. Read the task back:**

    $ karma task show WK2
    WK2  task
      title     Draft landing page copy
      status    TODO
      priority  P1
      project   ops
      agenda    WK1
      created   2026-10-21T01:56:56+05:30
      updated   2026-10-21T01:56:56+05:30
      body_mod  2026-10-20T20:27:06+00:00 (B+)
      body      /Users/alice/projects/website/.karma/work/WK2.md

    --- body ---
    # Landing page copy - plan

    1. Hero: one sentence on what the product unblocks.

The `B+` marker means the body file changed after the last CLI state mutation. It is a read-side hint, not a warning. See [Bodies](#44-bodies).

**8. Move the work:**

    $ karma task status WK2 DOING
    WK2: TODO -> DOING

**9. Deposit a decision into memory:**

    $ karma memory create --project ops --title "Ops decisions"
    ME1
      path  memory/ME1

    $ karma memory add ME1 --title "Why we moved the website" \
          --body "The old host raised prices 40 percent. The relaunch lands on flat-rate hosting." \
          --link WK1
    ME1#1
      title    Why we moved the website
      links    WK1
      path     /Users/alice/projects/website/.karma/memory/ME1/001-why-we-moved-the-website.md
      commit   0ec8029

**10. Check the workspace:**

    $ karma health
    all clear

That is the whole loop: create scope, create work, write the body, move the status, deposit what you learned, check health. Ten commands in, and the daily loop is already yours.

### 3.5 Where it all landed on disk

After the session above:

    .karma/
      karma.db                  # state: the items, scopes, counters, oplog
      work/
        WK1.md                  # agenda body (empty until you write it)
        WK2.md                  # task body, your landing page plan
        WK3.md  WK4.md
      memory/
        ME1/                    # one git repo
          001-why-we-moved-the-website.md

The database holds the state. The files hold the content. Both are yours to read with any tool.

## 4 Organizing work

Work is the day job. Projects give it scope, tasks and agendas give it shape, and the CLI keeps both honest. This chapter covers the whole surface.

### 4.1 Projects

A project is a scope with its own status and priority enums. Without explicit enums, a project gets the defaults:

    $ karma project create lab --title "Lab experiments"
    project lab created — statuses: OPEN, ACTIVE, PAUSED, DONE, DROPPED — priorities: LOW, MEDIUM, HIGH

    $ karma project list
    slug  title            statuses                             priorities         created
    ----  ---------------  -----------------------------------  -----------------  -------------------------
    lab   Lab experiments  OPEN, ACTIVE, PAUSED, DONE, DROPPED  LOW, MEDIUM, HIGH  2026-10-21T01:57:34+05:30
    ops   Operations       TODO, DOING, BLOCKED, SHIPPED        P1, P2, P3         2026-10-21T01:56:50+05:30

    $ karma project show ops
    ops  project
      title      Operations
      created    2026-10-21T01:56:50+05:30
      statuses   TODO, DOING, BLOCKED, SHIPPED
      priorities P1, P2, P3

The flags are optional. `karma project create dashboard` alone creates the project with default enums, but the title then stays empty forever. A project has no update path: slug, title, and enums stay as created, and there is no project delete. Choose them deliberately.

### 4.2 Tasks

    karma task create "<title>" [--project <slug>] [--agenda <id>] [--priority <name>]

- The title takes printable ASCII only. The full value policies live in [Timestamps, titles, and slugs](#84-timestamps-titles-and-slugs).
- With `--project`, the task gets the project's rank-1 status and priority. With `--agenda`, it gets a parent.
- `karma task list` filters by `--project`, `--status`, and `--agenda`, and shows archived items with `--all`.

### 4.3 Agendas

An agenda groups tasks. `karma agenda list` shows them:

    $ karma agenda list
    id   status  priority  project  agenda  arch  updated                    title
    ---  ------  --------  -------  ------  ----  -------------------------  ----------------
    WK1  TODO    P1        ops      —             2026-10-21T01:56:53+05:30  Website relaunch

`karma task list --agenda WK1` shows the direct children. Agendas do not nest, and an agenda cannot be a task's child.

**Moving an agenda is fail-fast.** An agenda with children in another project refuses to move:

    $ karma prop update WK1 --prop project --value lab
    {"error": "WK1 cannot move to project 'lab' — 1 child task(s) in project 'ops': WK2. Reconcile first, e.g.: karma prop clear WK2 --prop agenda && karma prop update WK2 --prop project --value lab"}

The error states the reconcile sequence. Follow it:

    $ karma prop clear WK2 --prop agenda
    WK2 agenda: WK1 -> cleared
    $ karma prop update WK1 --prop project --value lab
    WK1 project: ops -> lab (status: TODO -> OPEN) (priority: P1 -> LOW)
      note: status set to 'OPEN' (project default)
      note: priority set to 'LOW' (project default)

Two things happened in that move. The agenda changed projects, and the move **cascaded**: status and priority reset to the new project's defaults. The `notes` explain each cascade, so the post-state needs no follow-up read.

Re-attaching the task before it shares the new project fails loud:

    $ karma prop update WK2 --prop agenda --value WK1
    {"error": "project mismatch: WK2 project 'ops' vs agenda WK1 project 'lab' — a task and its agenda must share a project (or both be standalone)"}

A task and its agenda must share a project, or both be standalone. Re-scope the task, then attach:

    $ karma prop update WK2 --prop project --value lab
    WK2 project: ops -> lab (status: DOING -> OPEN) (priority: P1 -> LOW)
      note: status set to 'OPEN' (project default)
      note: priority set to 'LOW' (project default)
    $ karma prop update WK2 --prop agenda --value WK1
    WK2 agenda: — -> WK1

One boundary to keep in view: the error's suggestion stops at detach and re-scope. Moving the agenda and re-attaching the child are yours to complete, as this flow did.

### 4.4 Bodies

The body of a task or agenda is the whole markdown file. There is no frontmatter. Edit `.karma/work/WK<n>.md` directly with any editor. That is the designed path.

`karma task show` merges state with the body and reports a body marker:

- `B-`: the body file matches the last state mutation. A fresh create reads `B-`.
- `B+`: the body file changed after the last state mutation. The marker is a hint only. The CLI writes no state.

Body edits do not move `updated_at`. The marker is how you and your agents see that the file moved ahead of the state.

### 4.5 Status and priority

Statuses are free labels within a project's enum. Any value reaches any other value. The CLI enforces the enum at every mutation:

    $ karma task status WK2 ACTIVE
    WK2: OPEN -> ACTIVE

    $ karma task status WK2 SHIPPED
    {"error": "invalid status 'SHIPPED' for project 'lab' — valid: OPEN, ACTIVE, PAUSED, DONE, DROPPED"}

Standalone items reject status changes until they join a project:

    $ karma task status WK4 DOING
    {"error": "WK4 is standalone — attach to a project first: karma prop update WK4 --prop project --value <slug>"}

One design note here. Every property has exactly one mutation path. Status carries its own verb, `karma task status`, because it is the loop's most frequent move. Everything else mutates through `prop update`. Try the wrong path and the CLI names the right one:

    $ karma prop update WK2 --prop status --value ACTIVE
    {"error": "prop 'status' is managed by karma task status — single path per operation"}

### 4.6 Props

When unsure what an entity offers, ask prop first. `prop list` is read-only introspection, and it shows the allowed range inline:

    $ karma prop list WK2
    property    value                         mutability         via
    ----------  ----------------------------  -----------------  -------------------------------------------------------------
    id          WK2                           immutable          —
    type        task                          immutable          —
    created_at  2026-10-21T01:56:56+05:30     immutable          —
    updated_at  2026-10-21T01:58:08+05:30     system-maintained  the system
    title       Draft landing page copy       mutable            karma prop update WK2 --prop title
    project     lab                           mutable            karma prop update WK2 --prop project
    agenda      WK1                           mutable            karma prop update WK2 --prop agenda
    status      ACTIVE                        mutable            karma task status  |  [OPEN, ACTIVE, PAUSED, DONE, DROPPED]
    priority    LOW                           mutable            karma prop update WK2 --prop priority  |  [LOW, MEDIUM, HIGH]
    archived    0                             system-maintained  karma task archive
    body        80 bytes in work/WK2.md (B-)  implied            direct disk edit

The `via` column names the command that changes each property. That is the whole mutation model in one table.

`prop update` changes any mutable property on any work item or memory noun: tasks, agendas, memory spaces, memory items. Projects are not prop-addressable: they are immutable after create. The CLI deduces the noun from the ID prefix:

    $ karma prop update WK2 --prop priority --value MEDIUM
    WK2 priority: LOW -> MEDIUM (priority: LOW -> MEDIUM)

`prop clear` detaches. Only `project` and `agenda` are clearable, and clearing a project resets status and priority to standalone:

    $ karma prop clear WK3 --prop project
    WK3 project: ops -> cleared

    $ karma task show WK3
    WK3  task
      title     Buy SSL certificate
      status    — (standalone)
      priority  —
      project   —
      agenda    —
      ...

### 4.7 Archive and discard

**Archive** freezes a work item. Archived items reject every mutation until restored, and default listings hide them:

    $ karma task archive WK3
    WK3 archived

    $ karma task status WK3 SHIPPED
    {"error": "WK3 is archived — restore first: karma task archive WK3 --restore"}

    $ karma task archive WK3 --restore
    WK3 restored

Use `karma task list --all` to include archived items.

**An agenda archives only when its children allow it:**

    $ karma agenda archive WK1
    {"error": "WK1 has 1 unarchived task(s) (WK2) — archive or move them first"}

Archive the children first, then the agenda. No silent cascades.

**Discard** belongs to memory. It is destructive and gated (see [Discard](#57-discard)).

## 5 Memory

Memory is running knowledge: how decisions were made, what was tried, what to avoid. One agent deposits a lesson. Every future agent, you included, gets it instead of re-deriving it.

### 5.1 Spaces

One space per theme, not per task. The tour's step 9 created yours with `karma memory create --project ops --title "Ops decisions"`. The space lives at `.karma/memory/ME1/`, one git repo among many.

### 5.2 Items

An item is one authored markdown file:

    karma memory add <ME_n> --title "<title>" --body "<content>" [--link <target>]...

The tour added ME1#1. Add a second one, this time without a link:

    $ karma memory add ME1 --title "Hosting comparison" \
          --body "The new host quotes a flat rate. The old one billed by traffic."
    ME1#2
      title    Hosting comparison
      links    —
      path     /Users/alice/projects/website/.karma/memory/ME1/002-hosting-comparison.md
      commit   e3e7472

The file anatomy is absolute: line 1 title, line 3 links, body from line 5:

    # Hosting comparison

    links:

    The new host quotes a flat rate. The old one billed by traffic.

Lines 2 and 4 are blank. The links line is always present, even when empty. The filename slug derives from the title at creation and never changes.

### 5.3 Browsing discipline

Read the index, then the lineage, then only what you need:

    $ karma memory list
    id   items  project  updated                    last commit
    ---  -----  -------  -------------------------  -----------------------
    ME1  2      ops      2026-10-22T04:11:18+05:30  add: Hosting comparison

    $ karma memory show ME1
    ME1  memory
      title    Ops decisions
      project  ops
      path     /Users/alice/projects/website/.karma/memory/ME1

    id     title                     links  created
    -----  ------------------------  -----  -------------------------
    ME1#1  Why we moved the website  WK1    2026-10-22T04:11:23+05:30
    ME1#2  Hosting comparison        —      2026-10-22T04:12:39+05:30

    $ karma memory show ME1#1
    # Why we moved the website

    links: [Website relaunch](WK1)

    The old host raised prices 40 percent. The relaunch lands on flat-rate hosting.

    $ karma memory history ME1#1
    commit   date                       subject
    -------  -------------------------  -----------------------------
    0ec8029  2026-10-21T01:57:20+05:30  add: Why we moved the website

### 5.4 Links

Links connect an item to the work it explains. Targets:

| form | meaning |
|---|---|
| `WK<n>` | work item n (task or agenda, where archived is valid) |
| `ME<n>` | memory space n |
| `ME<n>#<m>` | memory item m of space n |
| `#<n>` | item n of the current space |

Shell users: quote a target that starts with `#` (as in `karma memory link ME1#2 "#2"`), or the shell treats it as a comment.

Validation is eager at every mutation. The target must exist. An item cannot link to itself or to its own space. Duplicate targets in one mutation fail loud. A typo fails at write time, not silently later.

    $ karma memory link ME1#1 WK2
    ME1#1 +1 — links: WK1, WK2 — commit eefc046

### 5.5 Editing items

Retitle or re-body through the prop noun. The file is re-authored. The filename keeps its birth slug:

    $ karma prop update ME1#1 --prop title --value "Why the relaunch happened"
    ME1#1 title: Why we moved the website -> Why the relaunch happened

    $ ls .karma/memory/ME1/
    001-why-we-moved-the-website.md  002-hosting-comparison.md

The link's text is the target's title at link time. Retitle the target later and the text goes stale, but the link still resolves.

One rule to keep in mind: write memory through the CLI only. The files sit on disk so any editor can read them, and hand edits surface as drift in `health`. See [House rules](#65-house-rules).

### 5.6 What belongs in memory

Memory holds **running knowledge**: decisions and their reasons, gotchas, handover notes, lessons that future sessions need.

Memory does not hold **produced outputs**. Plans, reports, and generated files belong to the project repo they serve, since that repo already owns versioning and proximity to the work. Link to them. Do not copy them in.

### 5.7 Discard

Discard destroys. The command asks for a y/N confirmation. `--yes` skips it in scripts, and `--json` mode requires it since the CLI skips prompts there:

    $ karma memory add ME1 --title "Renewal gotcha" \
          --body "The SSL renewal fires 30 days before expiry - calendar reminder is not enough."
    ME1#3
      title    Renewal gotcha
      links    —
      path     /Users/alice/projects/website/.karma/memory/ME1/003-renewal-gotcha.md
      commit   702a3af

    $ karma memory discard ME1#3
    discard ME1#3 — deletes /Users/alice/projects/website/.karma/memory/ME1/003-renewal-gotcha.md (inbound links will dangle; health reports them)? [y/N] y ME1#3 discarded — removed /Users/alice/projects/website/.karma/memory/ME1/003-renewal-gotcha.md

A space discard removes the database rows and the entire repo, and its fallout (the dangling link) gets fixed live in [The findings](#72-the-findings). A discarded ID never comes back: the sequence dangles forever. Discard never manages inbound links. The fallout surfaces through `health` as `dangling_link`, and the fix is `karma memory unlink`.

## 6 Working with agents

This is the chapter karma exists for. Agents bring throughput, you bring judgment, and the workspace is where the two meet.

### 6.1 The division of labor

The model: **an agent drives the loop, and a human reads the trail.** Agents create tasks, move statuses, edit bodies, and deposit memory. You review the trail, set the direction, and make the judgment calls. The commands are the same for both. The difference is who runs them most.

### 6.2 Agent setup

`karma init --with-skill` installs the `karma-usage` skill where agent harnesses discover it, by default `.agents/skills/` beside `.karma/`. The skill teaches agents the iron rules: mutate state only through the CLI, edit work bodies directly, keep memory CLI-only, run `health` when something looks off.

Every workspace also carries the primer and the bundled docs (see [What your agents receive](#33-what-your-agents-receive)). An agent that has never seen your workspace can orient in one read.

### 6.3 Parallel agents

Multiple agents can drive one workspace at the same time. Every mutation takes a database-level write lock, so two agents hitting the same memory space queue before either touches git. The consequences:

- **IDs interleave.** Two agents creating tasks get non-adjacent IDs. Never assume `id+1`. Parse the ID each create prints.
- **Contention is normal, not failure.** A rejected-then-retry loop under heavy parallel load is the design working.
- **Nothing corrupts silently.** A crash between the git step and the commit leaves a detectable state, and `health` reports it.

### 6.4 Reading the trail

Every state mutation writes one oplog row. `history` prints it, the state lineage of any work item:

    $ karma task history WK2
    seq  op      ts                         detail
    ---  ------  -------------------------  -----------------------------------------------------------------------------------------------------------------------------------
    3    create  2026-10-21T01:56:56+05:30  {"agenda": "WK1", "priority": "P1", "project": "ops", "status": "TODO", "title": "Draft landing page copy", "type": "task"}
    6    status  2026-10-21T01:57:13+05:30  {"from": "TODO", "to": "DOING"}
    9    clear   2026-10-21T01:57:51+05:30  {"from": "WK1", "prop": "agenda", "to": null}
    11   update  2026-10-21T01:58:01+05:30  {"from": "ops", "priority": {"from": "P1", "to": "LOW"}, "prop": "project", "status": {"from": "DOING", "to": "OPEN"}, "to": "lab"}
    12   update  2026-10-21T01:58:05+05:30  {"from": null, "prop": "agenda", "to": "WK1"}
    13   status  2026-10-21T01:58:08+05:30  {"from": "OPEN", "to": "ACTIVE"}
    14   update  2026-10-21T01:58:22+05:30  {"from": "LOW", "prop": "priority", "to": "MEDIUM"}

That one table answers the full story of a task: created under `ops`, worked, detached, moved to `lab` with its cascades, re-attached, re-statused, re-prioritized.

Memory items carry their lineage in git:

    $ karma memory history ME1#1
    commit   date                       subject
    -------  -------------------------  --------------------------------------
    a447244  2026-10-22T04:11:23+05:30  add: Why we moved the website
    e5687b4  2026-10-22T04:12:54+05:30  link: Why we moved the website (+ WK2)
    ff0a540  2026-10-22T04:12:57+05:30  title: Why the relaunch happened

Together these answer the two review questions: what happened to this work item, and what did the agents learn while doing it.

### 6.5 House rules

The rules your agents operate under, worth knowing because they explain everything the CLI does:

1. All state mutations go through the CLI. Never edit `karma.db`.
2. Work-item bodies: edit the md file directly.
3. Memory content: only through the CLI. Every mutation is one git commit.
4. Never hand-mint an ID. Parse what create prints.
5. Run `karma health` when something looks off. Fix causes, not symptoms.
6. When unsure what an entity offers, ask `karma prop list <id>` first.

### 6.6 The trust model

After any unusual event (a crash, a killed process, a restored backup), run `karma health`. The primer states the contract, agents follow it, and `health` catches every violation with a named finding and a fix path. If health is clean, the workspace is consistent. The philosophy behind this: [Drift is reported, not prevented](#27-drift-is-reported-not-prevented).

## 7 Health and recovery

karma assumes things go wrong sometimes (a crash, a hand edit, a discarded space) and it assumes you want to know. Health is how you know.

### 7.1 karma health

    $ karma health
    all clear

`health` compares the database against the disk and reports every finding. It exits 1 when it reports issues, so scripts and CI can gate on it. `karma health --json` emits the findings as JSON:

    {
      "status": "clean",
      "issues": []
    }

### 7.2 The findings

| finding | cause | fix |
|---|---|---|
| `dirty_repo` | a memory file was hand-edited | revert the edit, or redo the change through the CLI |
| `dangling_link` | a discard destroyed a linked space or item | `karma memory unlink <item> <target>` (batch-capable) |
| `missing_file` | a body file vanished | restore it, or investigate the loss |
| `orphan_file` | a stray file on disk | delete it, or adopt a memory item file by committing it in its space repo |
| `unparsable_item` | an item file lost its anatomy | restore line 1 title / line 3 links |
| `counter_reset` | a memory item file appeared with a sequence ahead of the counter (a hand-copied or restored file) | adopt it by committing the file in the space repo, or delete it |

The dangling-link loop, end to end. First the setup: a space gets linked, then discarded:

    $ karma memory create --title "Scratch space"
    ME2
      path  memory/ME2

    $ karma memory link ME1#1 ME2
    ME1#1 +1 — links: WK1, WK2, ME2 — commit 5bf91b5

    $ karma memory discard ME2 --yes
    ME2 discarded — removed /Users/alice/projects/website/.karma/memory/ME2

Health names the fallout:

    $ karma health
    1 issue(s):
      [dangling_link] ME1#1 — ME2 — missing space

The fix is one command, and health shows it:

    $ karma memory unlink ME1#1 ME2
    ME1#1 -1 — links: WK1, WK2 — commit 6901704
    $ karma health
    all clear

The dirty-repo loop, end to end. A hand edit to a memory file is off-contract, and health names it:

    $ echo "hand edit" >> .karma/memory/ME1/001-why-we-moved-the-website.md
    $ karma health
    1 issue(s):
      [dirty_repo] ME1 —  M 001-why-we-moved-the-website.md

Revert the edit, or redo the change through the CLI, and the workspace is clean again:

    $ git -C .karma/memory/ME1 checkout -- 001-why-we-moved-the-website.md
    $ karma health
    all clear

### 7.3 Fix causes, not symptoms

A finding names a cause. Fix the cause (revert the hand edit, unlink the dangle) instead of silencing the report. A finding you paper over returns.

### 7.4 Backup and recovery

State recovery is restoring the database files: `karma.db` plus its `-wal` and `-shm` sidecars. Content recovery is git, per memory space. Back up `.karma/` like any other project file. After restoring a backup, run `karma health`, since it re-aligns ID counters if the restore regressed them.

### 7.5 Upgrade

Run `karma upgrade` after installing a new binary. It applies pending schema migrations and refreshes `.karma/docs/` to match the binary:

    $ karma upgrade
    already current (schema v6)

Re-running `karma init` in an existing workspace is harmless: it regenerates `readme.md` and `docs/` and changes nothing else.

## 8 CLI conventions

Five minutes here makes every help screen readable. The CLI follows one grammar, one output contract, and one error style. Learn them once, and every command feels familiar.

### 8.1 Grammar and invocation

    karma <noun> <verb> [id] [--flags]

Nouns: `project`, `task`, `agenda`, `memory`, `prop`. System commands: `init`, `upgrade`, `health`, `version`, `help`. Properties are flags only. There are no positional properties.

- `--json` works at any position: `karma --json task list`, `karma task --json list`, and `karma task list --json` are equivalent.
- No value starts with `-`, so the `--` separator is never required.
- Every command except `init` walks up from the current directory to the nearest ancestor `.karma/`.
- `karma help <noun>` prints per-noun help. The task noun, for example:

| verb | description |
|---|---|
| `create` | create a task |
| `list` | list tasks |
| `show` | show a task (state merged with body) |
| `status` | set status (project enum) |
| `history` | the oplog, the state lineage |
| `archive` | archive this item (`--restore` to unarchive) |

### 8.2 Output modes

Default output is human-readable text. `--json` prints one valid JSON value on stdout (see [Scripting with JSON output](#94-scripting-with-json-output)).

Every `create` prints the new ID as the first line in human mode. Mutations return post-state. `task create`, `agenda create`, and `prop update|clear` return the envelope `{"id", "changed", "state"}`: `changed` lists every property the operation touched, auto-cascades included, and `notes` explains each cascade.

### 8.3 Errors

Errors are one JSON object on stderr with exit code 1:

    {"error": "project 'ops' already exists"}

Error text names the noun and, when applicable, the command that fixes the problem. Follow the suggestion. A wrong-noun call produces a correction, not a route:

    $ karma task show ME1
    {"error": "ME1 is a memory space — try: karma memory show ME1"}

Exit codes: 0 success, 1 error. `health` exits 1 when it reports issues.

### 8.4 Timestamps, titles, and slugs

- **Timestamps** are local time with UTC offset: `2026-10-21T01:56:56+05:30`. One exception: `body_mtime` renders in UTC.
- **Titles** take printable ASCII (32–126) only. The first character must be a letter, digit, underscore, or bracket. The CLI trims surrounding whitespace silently. Memory titles additionally bar the filename-hostile set: `/ \ : * ? " < > | # [ ]`.
- **Project slugs** take lowercase letters, digits, and dashes. The first character is a letter or digit. Slugs are unique and permanent.
- **Enum names** take capital letters, digits, dash, and underscore: no lowercase, no spaces, no special characters. Single-value enums are fine.

### 8.5 Command reference

**System**

| command | what it does |
|---|---|
| `karma init [--with-skill [DIR]]` | create `.karma/` here. Idempotent. `--with-skill` installs the agent skill |
| `karma upgrade` | apply pending schema migrations and refresh bundled docs |
| `karma health` | check database vs disk, report drift, exit 1 on issues |
| `karma version` | print the version (`karma --version`, `karma -v`) |
| `karma help [noun]` | top-level or per-noun help |

**project**

| command | what it does |
|---|---|
| `karma project create <slug> [--title <t>] [--statuses <s1,s2>] [--priorities <P1,P2>]` | create a scope with its own enums |
| `karma project list` | all projects |
| `karma project show <slug>` | one project |

**task**

| command | what it does |
|---|---|
| `karma task create "<title>" [--project <slug>] [--agenda <id>] [--priority <name>]` | create a task (prints the new ID first) |
| `karma task list [--project <slug>] [--status <name>] [--agenda <id>] [--all]` | list tasks (`--all` includes archived) |
| `karma task show <id>` | state merged with the body file |
| `karma task status <id> <state>` | set status (the CLI enforces the project enum) |
| `karma task archive <id> [--restore]` | freeze (or restore) the item |
| `karma task history <id>` | the oplog (the state lineage) |

**agenda**

| command | what it does |
|---|---|
| `karma agenda create "<title>" [--project <slug>] [--priority <name>]` | create an agenda (a parent of tasks) |
| `karma agenda list [--project <slug>] [--status <name>] [--all]` | list agendas |
| `karma agenda show <id>` | state merged with the body file |
| `karma agenda status <id> <state>` / `archive <id> [--restore]` / `history <id>` | same semantics as the task verbs |

**prop**

| command | what it does |
|---|---|
| `karma prop list <id> [--prop <name>]` | read-only introspection that shows allowed ranges inline |
| `karma prop update <id> --prop <name> --value <v>` | set any mutable property on any work item or memory noun |
| `karma prop clear <id> --prop <name>` | detach (clearable: `project`, `agenda`) |

**memory**

| command | what it does |
|---|---|
| `karma memory create [--project <slug>] [--title <t>]` | create a space (one git repo) |
| `karma memory add <ME_n> --title "<t>" --body "<content>" [--link <target>]...` | author one item, one git commit |
| `karma memory list [--project <slug>]` | the space index |
| `karma memory show <ME_n>` / `show <ME_n>#<seq>` | space index / one full item |
| `karma memory link <ME_n>#<seq> <target> [<target>...]` | append links (the CLI checks each target eagerly) |
| `karma memory unlink <ME_n>#<seq> <target> [<target>...]` | drop links (the dangling-link fix) |
| `karma memory history <ME_n> [--state]` / `history <ME_n>#<seq>` | git lineage of a space / an item (`--state` shows the space's oplog rows) |
| `karma memory discard <ME_n>` / `discard <ME_n>#<seq>` | destroy a space / an item (gated, `--yes` for scripts) |

## 9 Recipes

Concepts covered, commands at hand. Now the fun part. These patterns make karma click in daily use.

### 9.1 Solo mode

No agents in the picture? karma still works. Use a project as your board and tasks as your list. In a fresh workspace:

    $ karma project create personal --title "Personal" \
          --statuses "NOW,NEXT,WAITING,DONE" --priorities "HIGH,LOW"
    $ karma task create "Renew passport" --project personal
    $ karma task status WK1 NOW

Standalone tasks (no project) render as backlog: a holding pen for unsorted work. Attach them to a project when they earn a status.

### 9.2 The swarm

One workspace, several agents, one shared record:

    $ karma init --with-skill
    $ karma project create pica --title "Pica rebuild"
    $ karma agenda create "Migration wave 1" --project pica
    $ karma task create "Move auth service" --project pica --agenda WK1
    $ karma task create "Port the billing tests" --project pica --agenda WK1
    $ karma memory create --project pica --title "Pica decisions"

Then the loop, per agent:

1. `karma task list --project pica` shows the live work.
2. Work the task. Edit the body file directly as the plan evolves.
3. `karma task status WK2 DONE` records the transition.
4. `karma memory add ME1 --title "..." --body "..." --link WK2` deposits what was learned.

Or simply state the intent: with the skill installed, your agent translates it into these commands.

You read the trail (see [The human review loop](#96-the-human-review-loop)) and set the next direction. No agent holds context the others lack: the log and the memory space are the shared brain.

### 9.3 Custom vocabulary

Enums are per project, so each scope speaks its own language:

    $ karma project create ops --title "Operations" \
          --statuses "TODO,DOING,BLOCKED,SHIPPED" --priorities "P1,P2,P3"
    $ karma project create writing --title "Writing desk" \
          --statuses "DRAFT,EDITING,APPROVED,PUBLISHED"

A task in `ops` moves `TODO -> DOING -> SHIPPED`. A task in `writing` moves `DRAFT -> PUBLISHED`. The CLI enforces the owning project's enum at every mutation, so a typo fails loud with the valid range in the message.

### 9.4 Scripting with JSON output

`--json` works at any argv position and prints one valid JSON value:

    $ karma --json task list --project lab
    {
      "items": [
        {
          "id": "WK2",
          "type": "task",
          "title": "Draft landing page copy",
          "status": "ACTIVE",
          "priority": "MEDIUM",
          "archived": false,
          "project": "lab",
          "created_at": "2026-10-21T01:56:56+05:30",
          "updated_at": "2026-10-21T01:58:22+05:30",
          "agenda": "WK1"
        }
      ]
    }

Mutations return the envelope: `changed` lists every touched property, and `state` is the full post-state:

    $ karma --json task create "Json envelope demo" --project lab
    {
      "id": "WK5",
      "changed": {},
      "state": {
        "id": "WK5",
        "type": "task",
        "title": "Json envelope demo",
        "status": "OPEN",
        "priority": "LOW",
        "archived": false,
        "project": "lab",
        "created_at": "2026-10-22T04:14:42+05:30",
        "updated_at": "2026-10-22T04:14:42+05:30",
        "body_path": "/Users/alice/projects/website/.karma/work/WK5.md",
        "body": "",
        "body_missing": false,
        "body_mtime": "2026-10-21T22:44:42+00:00",
        "body_state": "B-",
        "body_dirty": false,
        "agenda": null
      }
    }

Two scripting rules. Parse the `id` from the create output. Never assume `id+1`. Gate on health: `karma health` exits 1 when it reports issues, so `karma health --json` plus the exit code is a ready-made CI check.

### 9.5 Memory patterns

Three patterns cover most needs:

- **Decision log.** One item per decision, linked to the task it explains. The body states the choice and the reason. Six months later, `karma memory show ME1#2` answers "why did we do this?"
- **Gotchas ledger.** One space per project for traps: the flaky test, the quirk in the deploy script. Agents read it before they re-derive the trap the hard way.
- **Session handover.** Before a long-running task pauses, deposit the state of the work: what is done, what is next, what is blocked. The successor agent, or you on Monday, starts from the item, not from archaeology.

### 9.6 The human review loop

Five commands, most days:

    $ karma health                          # is the workspace consistent?
    $ karma task list --project pica        # what is live, what moved?
    $ karma task show WK2                   # what does this task say now?
    $ karma task history WK2                # who did what, when?
    $ karma memory list --project pica      # what did the agents learn?

Deeper dives: `karma memory show ME1#2` for one lesson, `karma memory history ME1#2` for its lineage, `karma task list --all` to include archived work.

## 10 Troubleshooting and FAQ

When something behaves oddly, start here. Most confusion traces back to a handful of causes, and every error message names the fix.

### 10.1 Common errors decoded

Every error is JSON on stderr, exit 1, and names the command that fixes the problem. The common ones:

| error | meaning | what to do |
|---|---|---|
| `no .karma root found above <path> — run: karma init` | you are outside any workspace | `cd` into the project, or run `karma init` |
| `<id> is a memory space — try: karma memory show <id>` | wrong noun for that ID | follow the suggested command |
| `invalid status '<s>' for project '<slug>' — valid: ...` | the status is outside the project enum | use a valid value, or check `karma prop list <id>` |
| `<id> is standalone — attach to a project first: ...` | standalone items have no status | attach to a project, then set status |
| `<id> is archived — restore first: ...` | archived items reject mutations | restore, or leave it frozen |
| `<id> cannot move to project '<slug>' — N child task(s) ... Reconcile first` | the agenda move would orphan children | follow the stated reconcile sequence |
| `project mismatch: ... must share a project (or both be standalone)` | task and agenda scopes disagree | re-scope one of them, then attach |
| `prop '<name>' is not clearable — clearable: project, agenda` | only scope properties detach | change the value with `prop update` instead |
| `title contains characters outside printable ASCII (32-126)` | the CLI rejects emoji and multi-language characters | use printable ASCII in titles |
| `project '<slug>' already exists` | slugs are unique | pick another slug |
| `project '<slug>' not found — create it: karma project create <slug>` | the scope does not exist | follow the suggested command |

For drift findings (`dirty_repo`, `dangling_link`, and friends), see [The findings](#72-the-findings).

### 10.2 FAQ

**Can I edit `karma.db` directly?**
No. All state changes go through the CLI. Hand edits surface as drift in `karma health`.

**Where does my content live?**
Task and agenda bodies in `.karma/work/WK<n>.md`. Memory items in `.karma/memory/ME<n>/`. The database holds state only, never content.

**Can two agents corrupt the workspace?**
No. Mutations serialize at the database before either agent touches git. See [Parallel agents](#63-parallel-agents).

**How do I delete a task?**
You archive it. Deletion does not exist for work items, and IDs are never reused. Memory spaces and items discard (destructive and gated).

**Can I rename a project?**
The slug is permanent, and there is no project delete. A project is immutable after create: slug, title, and enums. Choose deliberately.

**What happens to an ID after archive or discard?**
It never comes back. A discarded memory item's sequence dangles forever rather than rebinding, so a stale link can only dangle and can never silently point somewhere new.

**Does karma have a graphical interface?**
No. The CLI and the files are the interface. Because content is plain markdown, every editor and Unix tool already works.

**Do I need git installed?**
Memory commands require git on PATH. Everything else works without it.

**Where do agents get their instructions?**
Every workspace ships the primer (`.karma/readme.md`) and the full command docs (`.karma/docs/`) after `karma init`. `karma init --with-skill` adds the `karma-usage` skill. See [Agent setup](#62-agent-setup).
